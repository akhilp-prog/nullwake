Freshness: the one check every table needs

If a table gets only one check, make it freshness. It is one line of SQL, but three details decide whether it catches a stopped load or quietly passes.

The check

A freshness check asks one question: when did new data last arrive? Take the newest load timestamp and compare it with the current time.

select max(loaded_at)         as newest,
       now() - max(loaded_at) as age
from analytics.fct_orders;

If the age is larger than you allow, the table is stale and someone should hear about it. That is the whole idea. The details below are what make it reliable.

Mistake 1: checking the business date

Tables usually have two kinds of timestamps: when something happened (order_date, event_time) and when the row reached the warehouse (loaded_at, _ingested_at, _fivetran_synced). Freshness needs the second one.

Business dates arrive late all the time. A delivery partner sends last week's orders today; a mobile app uploads events when the phone reconnects. A check on order_date flags those late rows as a stale table, and it can also pass while loads have stopped, if the last batch happened to include future-dated rows.

If a table has no load timestamp, add one in the loader or the first model. It is the most useful column you can add for monitoring.

Mistake 2: trusting max() when the future leaks in

One row with a timestamp next month makes max(loaded_at) look perfectly fresh for a month. Bad clocks, timezone bugs and test data all do this. Count rows from the future in the same query and treat any as a failure:

select now() - max(loaded_at) as age,
       count(*) filter (where loaded_at > now() + interval '5 minutes')
         as future_rows
from analytics.fct_orders;

The five-minute margin absorbs ordinary clock drift between servers.

Setting the limit

Start from the load schedule, then add slack for normal delays:

  • Loaded every 15 minutes: allow 45 to 60 minutes.
  • Loaded hourly: allow about 2 hours.
  • Loaded once a day at 02:00: allow about 26 to 28 hours.

Too tight and the alert fires on every slow night until people mute it. Too loose and the stale table is noticed by a stakeholder first. If you are unsure, look at the last few weeks of load times and set the limit just above the slowest normal one.

When one table has many sources

A table fed by several sources can look fresh while one of them has stopped: the busy source keeps max() current. If rows carry a source column, check each source separately:

select source,
       now() - max(loaded_at) as age
from analytics.fct_orders
group by source
order by age desc;

The top row is the source that has been quiet the longest.

Mistake 3: running it as a pipeline step

The most common setup is a freshness test that runs right after the load. It fails exactly when you need it: if the load never starts, the test never starts, and nothing turns red.

The check has to run on its own schedule, from something that does not depend on the pipeline. That is also why dbt source freshness only helps when it is scheduled on its own, not just as part of the same job that runs the models.

Snowflake and BigQuery

The query above runs on Snowflake as written if you replace count(*) filter (where …) with count_if(…), and use current_timestamp() for now() if you prefer. On BigQuery, use timestamp_diff(current_timestamp(), max(loaded_at), minute) and countif(…).

Both warehouses also record when a table last changed (last_altered in Snowflake's information_schema.tables, last_modified_time in BigQuery's table metadata). That is useful when a table has no load column, but it is a weaker signal: any update or delete also moves it, so a table can look fresh without new rows.

Doing this with Nullwake

In a Nullwake data contract, freshness is two lines: the column and the limit. Nullwake runs it on its own schedule, treats future timestamps as a failure, opens an incident for the team that owns the table, and closes it when fresh data arrives.
