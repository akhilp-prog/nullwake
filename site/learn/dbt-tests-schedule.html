Why your dbt tests miss things

If you use dbt, you have already written good data quality rules. The catch is when they run: only when dbt does. When a load stalls, dbt has nothing to run, and every test stays green.

By Akhil Pettem · 2026-11-25

On this page

  1. What dbt tests do well
  2. The gap: tests run with the build
  3. Closing the gap
  4. Give every failure an owner
  5. Doing this with Nullwake

What dbt tests do well

dbt's generic tests describe what good data looks like, right next to the models:

models:
  - name: orders
    columns:
      - name: order_id
        tests: [unique, not_null]
      - name: status
        tests:
          - accepted_values:
              values: [placed, shipped, completed, returned]
      - name: customer_id
        tests:
          - relationships: {to: ref('customers'), field: customer_id}

These are exactly the rules a data team should have. Most teams that use dbt already have dozens of them. The gap is not the rules; it is when they run.

The gap: tests run with the build

A dbt test runs when someone runs dbt test or dbt build, usually as part of the scheduled job that builds the models. That creates three blind spots:

  • The load never arrives. If the source data stops, the job may still run and test yesterday's data, which passes. If the job itself is skipped or fails before the test step, no tests run at all.
  • Between runs. A daily build tests the data once a day. Anything that breaks after the build is invisible until the next one.
  • Freshness isn't scheduled. dbt can check source freshness with loaded_at_field and freshness settings, but only when someone runs dbt source freshness. Many teams configure it and never schedule it, or run it inside the same job that is supposed to be monitored.

Each of the failures from this series, a stale table, a partial load, a renamed column, can therefore slip past a project with good tests.

Closing the gap

Three steps, in order of effort:

  1. Schedule source freshness on its own. Run dbt source freshness as a separate job every hour or so, independent of the build. If the build job breaks, this one still runs and still alerts.
  2. Add a volume expectation to your most important sources, as in the volume guide. Fresh but half-empty is the failure dbt's built-in tests miss most often.
  3. Run the important tests on a schedule too, not only after builds, and route failures to the team that owns the model, not a shared channel.

Give every failure an owner

A failing test in a CI log is a fact; an alert that reaches the team that owns the table is something that gets fixed. dbt has a place for this already: meta: {owner: …} on models and sources, and groups with owners. Fill it in for the tables that matter, and use it to route alerts.

Doing this with Nullwake

This is the gap Nullwake was built for. Point it at your dbt manifest and it drafts one data contract per model from the tests you already have:

dbt parse     # writes target/manifest.json
nullwake init connection.yaml --dbt target/manifest.json
  • unique and not_null become column rules.
  • accepted_values and relationships become SQL checks.
  • A source's loaded_at_field and freshness become the freshness check.
  • meta.owner or the group owner becomes the contract owner.

Nullwake then runs those checks on their own schedule, adds freshness and volume, opens an incident for the owning team when one fails, and closes it when the data recovers. It runs inside your network and reads only counts and aggregates. Tried on dbt Labs' jaffle_shop: every carried-over test passes on the built project and fails when a bad row is inserted.
