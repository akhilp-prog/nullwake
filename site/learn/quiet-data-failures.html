Data that is wrong without anything failing

The costliest data problems in a warehouse don't raise an error. Here are the five that show up most often, what each looks like, and one SQL check that catches it.

Why nothing fails

A load stops overnight. Nothing errors. The dashboard still shows numbers, just yesterday's. Someone makes a decision on them before lunch, and the data team hears about it from the person who made it.

This happens because most pipeline monitoring answers one question: did the code run? Orchestrators report failed tasks. dbt reports failed tests. But a task that never started can't fail, and a dbt test only runs when dbt runs. If the problem is in the data rather than in the code, nothing turns red.

The fix is to check the data itself, on its own schedule, separately from the pipeline that loads it. Five checks cover most of what goes wrong.

The queries below are written for Postgres and tested on it. Snowflake runs them with small changes (use count_if instead of filter), and BigQuery needs its own date functions and countif; the checks themselves are the same.

1. The table stopped updating

What it looks like: numbers that look normal but stop moving. A loader lost its credentials, an upstream export was paused, or a scheduler skipped a run.

Why it's missed: no step fails. The load simply doesn't happen, so nothing downstream runs either.

The check: compare the newest load timestamp with the current time.

select now() - max(loaded_at) as age
from analytics.fct_orders;

Alert when the age is larger than the load schedule plus some slack: a table loaded hourly might allow 90 minutes. Use the load timestamp, not a business date, because an order placed last week can arrive today. Treat timestamps in the future as a failure too: one bad row dated next month can hide a load that stopped yesterday.

2. The load ran, but half the rows are missing

What it looks like: the table is fresh, but totals are low. An API paginated early, a file arrived truncated, or a filter changed upstream. The opposite happens too: a backfill runs twice and a day is doubled.

Why it's missed: the freshness check passes, because rows did arrive.

The check: count rows in the latest window and compare with recent windows.

with daily as (
  select date_trunc('day', loaded_at) as day, count(*) as n
  from analytics.fct_orders
  where loaded_at >= now() - interval '15 days'
  group by 1
)
select
  (select n from daily
    where day = date_trunc('day', now() - interval '1 day')) as yesterday,
  percentile_cont(0.5) within group (order by n) as typical
from daily
where day < date_trunc('day', now() - interval '1 day');

Compare with the median of recent windows rather than a fixed threshold. A fixed "alert below 10,000 rows" breaks on weekends, holidays and growth. The median also keeps one bad day from shifting the baseline, which an average would not.

3. A column changed upstream

What it looks like: a team renames customer_id to cust_id, or changes an amount from a number to text. Their deploy goes fine. If your model selects * or joins loosely, the column quietly becomes NULL and every downstream number shifts.

Why it's missed: many transformations don't fail on a missing column; they return NULL.

The check: compare the columns the warehouse has with the columns you expect.

select column_name, data_type, is_nullable
from information_schema.columns
where table_schema = 'analytics'
  and table_name = 'fct_orders'
order by ordinal_position;

Alert when a column you rely on is missing or has changed type. Keep the expected list in your repository, reviewed in pull requests. That list is a data contract with the team that sends you the data.

4. A key column started filling with NULLs

What it looks like: row counts are right and the schema is unchanged, but a join key or required field is suddenly empty for some rows. Usually a new code path upstream stopped setting it.

Why it's missed: NULLs are valid values. Joins drop those rows silently, and sums come out lower without any error.

The check:

select count(*) filter (where customer_id is null) as null_keys
from analytics.fct_orders
where loaded_at >= now() - interval '1 day';

For columns that must never be empty, the threshold is zero. For optional columns, compare the null rate with its recent history the same way as volume.

5. The same rows arrived twice

What it looks like: revenue jumps, then someone finds every order from Tuesday counted twice. A retry, a replayed event stream or a backfill without a merge key.

Why it's missed: the data looks plausible. Bigger numbers rarely trigger alarms on their own.

The check:

select count(*) - count(distinct order_id) as duplicates
from analytics.fct_orders;

On large tables, limit it to recent data, or check the key over the latest load window only.

Run the checks on their own schedule

All five checks share one rule: they must run even when the pipeline doesn't. If they run as a step after the load, a load that never starts means checks that never start, and the first failure above slips straight through.

A practical starting point for a team with no data monitoring yet:

  • Pick the five tables that decisions depend on: the ones behind your revenue, usage or operations dashboards.
  • Add freshness and volume checks to each. They catch most incidents.
  • Add a schema check to every table that another team sends you.
  • Send each alert to the team that owns the table, not to a shared channel everyone mutes.
  • Close the alert automatically when the data recovers, so the open list stays short and trusted.
