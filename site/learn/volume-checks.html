Volume: on time, but half the rows

A table can be fresh and still be wrong: the load ran on time but brought half the rows, or ran twice. A volume check catches both, if you compare against the right baseline.

By Akhil Pettem · 2026-11-25

What freshness misses

An API returns its first page and stops. A file lands truncated. An upstream filter changes and drops one country. In every case rows still arrive on schedule, so a freshness check passes.

The reverse happens too: a retry or a backfill without a merge key loads a day twice, and revenue for that day doubles. Bigger numbers rarely look like an error.

A volume check counts rows in the latest window and asks whether that count is normal.

Why a fixed threshold fails

The first version most teams write is "alert if fewer than 10,000 rows". It breaks within weeks:

  • Weekends and holidays are quieter, so it fires every Sunday.
  • The business grows, so a load that drops 30% still clears the old minimum.
  • Nobody remembers to update the number.

The fix is to let the table's own history decide what normal is.

Compare with the median, and measure the spread

Count rows per day for the last few weeks, then compare yesterday with the typical day. Use the median rather than the average, so one bad day does not drag the baseline with it. For the spread, use the median absolute deviation (MAD): how far a typical day sits from the median.

with daily as (
  select date_trunc('day', loaded_at) as day, count(*) as n
  from analytics.fct_orders
  where loaded_at >= current_date - 29
    and loaded_at < current_date - 1
  group by 1
),
stats as (
  select percentile_cont(0.5) within group (order by n) as median
  from daily
),
spread as (
  select percentile_cont(0.5) within group (order by abs(d.n - s.median)) as mad
  from daily d cross join stats s
),
latest as (
  select count(*) as n
  from analytics.fct_orders
  where loaded_at >= current_date - 1
    and loaded_at < current_date
)
select l.n as yesterday, s.median, p.mad,
       abs(l.n - s.median) > 4 * greatest(p.mad, 1) as anomalous
from latest l, stats s, spread p;

Yesterday is counted separately, so a day with no rows at all still comes back as 0 and is flagged, rather than disappearing from the result. Flag a day that sits more than about four MADs from the median. That is wide enough to ignore ordinary noise and narrow enough to catch a half load or a doubled one. The greatest(…, 1) keeps a perfectly steady table from flagging a difference of a single row.

Weekly patterns

If Mondays are always twice as busy as Sundays, comparing a Sunday with the median of all days will look like a drop every week. Compare with the same weekday instead: add and extract(dow from loaded_at) = extract(dow from current_date - 1) to the daily step, and widen the window to eight or ten weeks so there are enough samples.

Start with the plain version. Switch to same-weekday only for tables where the plain one actually cries wolf.

Choosing the window

  • Daily loads: count by day, as above.
  • Hourly or streaming loads: count by hour, and compare the last complete hour with the same hour on previous days.
  • Always use complete windows. Counting today while today is still loading will look like a drop every morning.
  • Count by load time, not business time, for the same reason as freshness: late-arriving rows move between days otherwise.

Snowflake and BigQuery

Snowflake supports percentile_cont … within group as written; use dateadd(day, -1, current_date) or keep the date arithmetic as shown. In BigQuery, use timestamp_trunc(loaded_at, day), date_sub(current_date(), interval 1 day), and approx_quantiles(n, 2)[offset(1)] for the median.

Doing this with Nullwake

Nullwake's volume check uses this median and MAD baseline over recent windows, so there is no row count to maintain. tolerancePct sets a minimum band around the median, so a very steady table does not alert on small changes:

volume: {column: loaded_at, windowHours: 24, tolerancePct: 50}

When a window falls outside the expected range, it opens an incident for the owning team with the count and the expected range, and closes it when volume is back to normal. Try it in the live demo, which simulates a partial load and a duplicate load on a schedule. Previous guide: freshness.
