Schema drift: someone renamed a column upstream

An upstream team renames a column and their deploy goes fine. Yours often does too, and that is the problem: the column quietly becomes NULL and every downstream number shifts.

By Akhil Pettem · 2026-11-25

Why nothing breaks

A team renames customer_id to cust_id, changes amount from a number to text, or drops a column they think nobody uses. Some of your models fail loudly, which is the good case. The bad cases are quieter:

  • A model that selects * simply no longer has the column, and a later step fills it with NULL.
  • A join on the renamed key matches nothing, so a left join returns NULLs and an inner join returns fewer rows.
  • A number stored as text still sums in some tools, or sorts wrongly in others.

The check is to compare the columns that exist with the columns you depend on, before anything downstream reads them.

The check

Every warehouse describes its own tables in information_schema.columns. Write down the columns you expect, and compare:

with expected(column_name, data_type) as (
  values ('order_id',    'bigint'),
         ('customer_id', 'bigint'),
         ('amount',      'numeric'),
         ('loaded_at',   'timestamp with time zone')
),
actual as (
  select column_name, data_type
  from information_schema.columns
  where table_schema = 'analytics' and table_name = 'fct_orders'
)
select coalesce(e.column_name, a.column_name) as column_name,
       e.data_type as expected_type,
       a.data_type as actual_type,
       case when a.column_name is null then 'missing'
            when e.column_name is null then 'new'
            else 'type changed' end as problem
from expected e
full join actual a on a.column_name = e.column_name
where a.column_name is null
   or e.column_name is null
   or a.data_type <> e.data_type;

No rows back means the table matches. Any row is a difference, with the reason next to it.

Which differences to alert on

  • Missing column: always alert. Something downstream almost certainly reads it.
  • Type changed: always alert. Even a widening change, such as integer to bigint, is worth a look; a number becoming text never is harmless.
  • New column: usually fine. Alert only on tables that should be locked down, such as tables shared with other teams or with personal data, where a new column can mean data you did not agree to receive.

Column order rarely matters, and checking it causes noise. Leave it out unless a consumer reads columns by position.

The expected list is a data contract

The values list in the query is the most valuable part. Keep it in your repository next to the models, and review changes to it in pull requests. Then a schema change becomes a conversation before the deploy rather than an incident after it.

It also answers a question many teams cannot: who agreed to what? If the team that produces the table owns the list, they know a rename will break you before they ship it.

When to run it

Run schema checks on tables that other teams or tools write to: raw loads from SaaS connectors, event streams, tables owned by an application team. Those are the ones that change without your code changing. Run it on a schedule, like freshness, not only during your pipeline: the change usually lands between your runs.

Snowflake and BigQuery

Snowflake stores names in upper case unless they were quoted, so compare with upper(column_name) or list the expected names in upper case; types read as NUMBER, TEXT and TIMESTAMP_TZ. In BigQuery, query `project.dataset.INFORMATION_SCHEMA.COLUMNS` with where table_name = 'fct_orders'; types read as INT64, NUMERIC, STRING and TIMESTAMP.

Doing this with Nullwake

In a Nullwake data contract the expected columns are the schema section, reviewed in pull requests like any other code:

schema:
  allowAdditionalColumns: true
  columns:
    - {name: order_id, type: bigint, nullable: false}
    - {name: customer_id, type: bigint}
    - {name: amount, type: numeric}
    - {name: loaded_at, type: timestamptz}

Nullwake compares it with the warehouse on a schedule, opens an incident naming the missing or changed column for the owning team, and lets an editor accept an intended change in one click. nullwake init drafts the list from your existing tables, so you do not type it by hand.
