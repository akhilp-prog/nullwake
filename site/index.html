Know your data broke before anyone opens the dashboard.

Nullwake checks your warehouse tables against data contracts written in YAML. When a table goes stale, shrinks, changes shape or breaks a business rule, it opens an incident, alerts the team that owns it, and closes the incident once the data is healthy again. It runs inside your network and reads only counts and aggregates.

What it catches

Most data incidents are found by the person reading the dashboard. A loader stalls overnight, an upstream team renames a column, a backfill doubles a day of payments. Nullwake turns each of those into a promise the producer writes down and a check that runs on schedule.

How it works

Contracts live in your repository next to your dbt models and change through pull requests, like the rest of your code.

  1. Write the contract

    One YAML file per table: who owns it, how fresh it must be, its columns, its keys and any rules of your own.

  2. Apply it from CI

    nullwake apply contracts/ loads the contracts. nullwake check can also run every contract straight after dbt build and fail the pipeline, with no server needed.

  3. Checks run on schedule

    Workers run each check on its own interval through a read-only warehouse role, with a statement timeout on every query.

  4. Incidents open and close themselves

    A failing check opens one incident, not a stream of alerts. The owning team hears about it in Slack or through a signed webhook, can acknowledge it and add notes, and the incident closes when the check passes again.

contracts/orders.yaml
apiVersion: nullwake/v1
kind: DataContract
metadata:
  name: orders
  owner: commerce-data@example.com
spec:
  connection: warehouse
  dataset: analytics.fct_orders
  schedule: {intervalMinutes: 15}
  schema:
    columns:
      - {name: order_id, type: bigint, nullable: false}
      - {name: amount, type: numeric}
      - {name: loaded_at, type: timestamptz}
  uniqueKey: [order_id]
  freshness: {column: loaded_at, maxAgeMinutes: 90}
  volume: {column: loaded_at, windowHours: 24}
  checks:
    - name: no_negative_amounts
      sql: select count(*) from analytics.fct_orders
           where amount < 0

Runs inside your network

Nullwake is a set of containers you run next to your warehouse, on one VM or your own container platform. Your rows never leave, and neither do your credentials.

Read-only by construction
Checks run in read-only transactions with a statement timeout. Table and column names are validated, never pasted in from free text, and a custom rule must be a single SELECT.
No rows leave the warehouse
Built-in checks read back counts and aggregates only. Warehouse error messages are cut down to their error code before they are stored or logged.
Credentials stay in your environment
Contracts name an environment variable instead of holding a password, and a contract with an inline secret is rejected.
Nothing phones home
No telemetry and no licence server. The only outbound traffic is the alerts you configure and an optional heartbeat ping you point at your own monitor.
Every line is readable
Apache 2.0 source, an audit log of every sign-in and change, roles for viewers, editors and admins, and a web interface that ships no JavaScript.

Built never to show a false green

A monitor that says “passing” while the data is broken is worse than no monitor. Each of these came out of an external review and is covered by a regression test.

  • Empty answers are errors

    A rule that returns NULL or a non-number is reported as an error. It never counts as a pass and never closes an incident.

  • Future timestamps fail freshness

    One bad row dated next week can’t hide a load that stopped yesterday.

  • Late results are thrown away

    If a worker loses its claim on a check, its result is discarded, so an old “pass” can’t close a newer incident.

  • Alerts survive crashes

    Alerts are written in the same transaction as the incident and retried until delivered.

  • It watches itself

    A health endpoint for your uptime monitor turns red when checks are overdue, workers are silent or alerts are stuck.

  • History is never deleted

    Removing a check retires it. Its runs, incidents and audit trail stay, and re-adding it brings them back.
